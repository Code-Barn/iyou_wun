# Project Design Doc: The Sovereign Media Stack

**Status:** Initial Specification

**Core Technologies:** Django (Backend), React (PWA), Rust (IdP & Tauri), Blossom/Nostr/XMPP (Protocols).


## 1. Architectural Overview

The system is designed as a **decentralized service mesh**. It decouples Identity (DID), State (Nostr), and Data (Blossom).

### The "Sovereign Trinity"

| **Layer** | **Component** | **Implementation** |
| - | - | - |
| **Identity** | **IDP Bridge** | Rust-based DID module handles Auth and provides Schnorr keys for signing. |
| **State** | **Nostr Relay** | Django acts as a gateway to store and broadcast video/microblog metadata. |
| **Data** | **Blossom Server** | Content-addressed storage (SHA-256) for videos and blobs. |


## 2. Implementation Phases

### Phase 1: The Identity & Auth Bridge (The "First Brick")

We must bridge the **Rust IdP** with the **Django Backend**.

- **The Signer:** The Rust IdP manages the `secp256k1` keys.

- **Session Management:** Django should not store private keys. It validates a **NIP-98 (HTTP Auth)** or **DID-signed header** generated by the IdP/Frontend.

- **Action for Devs:** Implement a Django Middleware that intercepts requests, communicates with the Rust IdP module to verify the signature, and populates a `request.sovereign\_user` object.

### Phase 2: Blossom Storage Engine (Django)

Instead of standard file uploads, we implement the **Blossom Protocol (BUD-01/02)**.

- **Logic:** Files are saved by their **SHA-256 hash**.

- **Deduplication:** Before saving, Django checks if the hash exists. If yes, it just creates a database link to the existing file.

- **Integrity:** On every `GET` request, the server (or client) can verify the file matches the hash in the URL.

### Phase 3: The Unified Frontend (React + Tauri)

The frontend must be a **PWA** with an optional **Tauri Desktop Service**.

- **React PWA:** The primary UI. It uses the Rust IdP to sign messages.

- **Tauri Service:** A background agent that allows "Local Custody."

  - If Tauri is active, the React app sends uploads to `localhost` (Tauri) instead of the Django server.

  - Tauri handles local IPFS pinning and local Blossom hosting.


## 3. Tech Stack & Security Audit

### Security Highlights & Best Practices

You mentioned a priority on security. Here is the "Threat Landscape" for your chosen stack:

| **Technology** | **Known Security Risks** | **Mitigation Strategy** |
| - | - | - |
| **Django (Python)** | SQL Injection, XSS, CSRF. | Use the ORM exclusively. Enable `SECURE\_BROWSER\_XSS\_FILTER`. Use `argon2` for any legacy password hashing. |
| **Rust** | `unsafe` blocks, Logic errors in crates. | Minimize `unsafe` code. Use `cargo-audit` to check for vulnerable dependencies. |
| **React** | Cross-Site Scripting (XSS) via `dangerouslySetInnerHTML`. | Use automated sanitization (DOMPurify). Avoid direct DOM manipulation. |
| **Nost/Blossom** | Replay Attacks. | Implement **NIP-98** style headers with expiration timestamps and `u` (url) tags to prevent signature reuse. |

> **Security Note:** In a decentralized system, the **Client** is the most vulnerable point. Since the client handles private keys (via the Rust IdP), ensure that the key-signing memory is cleared and never exposed to the JavaScript runtime directly (use the Rust module as a "Black Box" signer).


## 4. Initial Developer Prompts (Direct to Coding Agents)

### Task A: The Blossom Backend

> "Create a Django app named `storage`. Implement a `PUT` endpoint that accepts a binary stream. Use `hashlib` to calculate the SHA-256 of the incoming data. Store the file in a directory structure based on the hash (e.g., `/media/blossom/ab/cd/ef...`). Ensure the response is BUD-01 compliant, returning the hash, size, and type. Authentication must be verified via our Rust DID module."

### Task B: The Nostr Metadata Event

> "Implement a utility in the React frontend to generate a NIP-94 (Kind 1063) event. The event must include tags for the Blossom URL (`url`), the SHA-256 hash (`x`), the size (`size`), and an optional IPFS CID (`cid`). The event must be signed using the Rust IdP bridge before being broadcast to the Django relay."


## 5. Design Philosophy: "One App, Many Views"

Instead of separate subdomains for video, microblogging, and cloud storage, we use a **Single Feed Architecture**:

- **Unified Post:** Users click "Create." They can type text, record video, or upload a file.

- **Dynamic Rendering:** The frontend looks at the `kind` of the Nostr event.

  - `kind:1` -\> Render as a Microblog post.

  - `kind:34235` -\> Render in a "YouTube-style" video player.

  - `kind:1063` -\> Render as a "Downloadable File" (Cloud Storage).
